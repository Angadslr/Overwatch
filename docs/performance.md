# T22 resource and failure measurements — open findings

Measured 25–26 October 2026 on Apple M4 Pro/macOS arm64 with Cursor 3.26.16. T22 remains incomplete: near-cap memory, idle CPU and loaded helper latency exceed their targets. Production broker transport and installed-editor burst delivery now reconcile every expected event. G3 and T24 packaging remain gated on resolution or an explicit reviewed scope/budget decision.

The [helper measurement](t22-helper-measurement.json) records one first launch and 100 repeated fresh-process samples on Node 24.21.0. First response/close took 11.85/23.38 ms; repeated response p50/p95 was 4.33/4.74 ms and process-close p50/p95 was 14.09/15.95 ms. Maximum reported helper RSS was about 6.7 MiB. First launch does not mean forced cold OS caches; timings include process startup and `/usr/bin/time`, and the CPU report is quantized.

The [burst isolation measurement](t22-burst-isolation.json) removed the UI and attempted 2,000 publications. A repeat of this legacy isolation run accepted 1,096 of 2,000 records; its helper close p95 was about 2,135 ms. The earlier run accepted 1,053 with 16 rejections and 17 failures. The helper's response-first behavior does not establish durable telemetry delivery. Publication/deadline failures now leave a bounded private, content-free producer-loss marker where possible; Source Health reports the loss without claiming an exact missing-event count. Failure to write that marker is still possible during storage failure.

The [near-cap measurement](t22-history-cap-measurement.json) opened 97,280 synthetic records occupying 104,856,734 source bytes. Open/validation/first projection took about 898 ms. Incremental RSS was 166,100,992 bytes, exceeding the proposed 75 MiB target. This measures a separate Node process; shared extension-host memory and complete UI replay are not established by this result. Load generation was subsequently moved outside the extension host so harness allocation is not charged to extension CPU/memory.

The [native missing-helper failure smoke](t22-native-failure-smoke.json) passed: an ordinary Cursor native read completed while the copied development helper executable was absent. The view remained awaiting its first native event, with no telemetry incorrectly claimed. The copied helper was restored and the owned fixture disabled with hooks/lease absent and inbox empty. This proves that named missing-executable scenario, not every OS/runtime failure or comparative latency target.

These artifacts predate T23's generation-specific inbox upgrade. Reproduce resource measurements against the final transport before closing T22; do not treat the historical values as current performance qualification. Existing focused scripts are `scripts/measure-helper.mjs`, `scripts/measure-burst.mjs`, `scripts/measure-history-cap.mjs` and the installed-host performance harness.


## Current implementation and comparable replay measurements

The T22 continuation is split into bounded history, idle rendering and transport feasibility work. The production journal retains the most recent 5,000 full source records plus a chunked binary digest/sequence/time index for all retained UUIDs. Older payloads remain on disk and can be read in bounded internal pages; Source Health discloses the buffered/retained counts and starting sequence. Replay validates every stored row using 64 KiB reads. A sequence cursor keeps fresh delivery working as the fixed-length tail moves. Reducer deduplication stores each namespace once rather than repeating its text in every retained key. Current source validation, privacy filtering, unknown-state semantics and historical cleanup remain enforced.

The old and new implementations were measured using the same fresh child-reader harness and 97,280-record, 104,856,734-byte input, projecting 5,000 facts in each case. The [original owned T22 bundle](t22-history-original-comparable.json) used 345,849,856 incremental RSS bytes (about 330 MiB) and 199,297,824 heap bytes. The [compact/streamed implementation](t22-history-window-measurement.json) measured 209,190,912 RSS bytes (about 199 MiB) and 114,857,488 heap bytes. This reduces measured peak RSS by about 40%, but **does not meet 75 MiB**. The original reader retained all payloads; the new reader retains a recent tail. Validation/first projection in the new sample took about 2.47 seconds with visible staged loading. The earlier 166 MiB artifact used a different baseline and is not a direct comparator. These samples have zero retired identities and do not establish the worst-case tombstone-memory bound.

## Installed-host timing and idle controls

Installed Cursor API 1.128.0/Node 24.19.0 runs continued to meet normal-load targets. In the CPU-control run, 40 samples at 20 events/second measured about 19.7 ms helper-close p95 and 251 ms matching-provider-row p95. The first/warm native-cache distinction remains explicit; no forced cold-cache result or paint timing is claimed.

Production burst delivery remains incomplete. That same run observed 1,255 of 2,041 expected first/normal/burst records. [Generation-specific producer-only testing](t22-burst-producer-only.json) accepted 1,069 of 2,000 attempts. [GOMAXPROCS=1](t22-burst-single-runtime.json) and [desktop execution outside the shell sandbox](t22-burst-desktop-producer.json) did not resolve the loss. No runtime override or weakened sync requirement was introduced.

Clock-only visible tree refreshes now occur at most every ten seconds; new data still takes the existing immediate/batched path. Hidden views skip clock refreshes. Time-filter clocks and uncertainty boundaries remain checked each second. Decoration caching lasts until its next receipt/expiry boundary. Queue-only health samples no longer rebuild activity. Healthy named watcher wakeups remain immediate; an empty watched queue backs polling off to one second. Unavailable watchers keep the configured faster polling fallback. A coalesced wake flag prevents publication notifications received during a scan from being lost. Watcher rename filtering excludes directory/temporary-file noise; periodic scans still cover unnamed or missed notifications.

Earlier 3-second "idle" samples overlapped the 30-second expiry/uncertainty transitions. The harness now reports transitions separately and samples settled idle for 15 seconds after the last accepted receipt is at least 31 seconds old. One bounded-clock run reduced settled shared-host CPU from about 11.7% to 3.45%, still above 1%. A later control run measured 1.08% disabled, 4.39% empty-enabled and 5.25% loaded idle (estimated incremental difference 4.17 percentage points). These samples predate the final watcher-backoff change. A subsequent host closed without a result; it is unqualified. Native watcher/backoff tests passed outside the shell sandbox, which otherwise refuses watcher registration. Final idle CPU must be remeasured before closing the gate.

## Durable batch feasibility and journal foundation

Go microbenchmarks measured about 4.14 ms per file-data sync and 4.67 ms per directory-entry sync, and 10.43/11.27/14.85 ms total publication with 0/512/2,048 queued files. These are isolated local microbenchmarks, not a universal device throughput guarantee.

The [disposable batch-writer prototype](t22-batch-transport-prototype.json) persisted and acknowledged all 2,000 synthetic records at 200/second for ten seconds. Helper-close p95 was 21.8 ms, with 810 write/sync groups and a maximum queue of 61. Each client acknowledgment followed a completed journal sync. It uses a private temporary Unix socket; no network upload occurs. The client ignores native stdin and sends a random ID; the writer constructs fixed synthetic metadata. It does **not** exercise production source admission, privacy, leases, spool fallback, generation reset or interrupted broker recovery. This result supports investigating batching, not a production T22 pass.

The journal now has a serialized `appendBatch` API for at most 32 envelopes. It shares data sync within each bounded durable group, validates source/scope and optional admission callbacks, rejects conflicting identities, preserves sequence/idempotence and whole-segment retention, and resolves only after sync. Single-record spool appends use the same serialized writer. Collector shutdown waits for queued journal writes. This foundation is complete and tested; a production broker is not connected and the Go hook still publishes through the spool. Do not claim that the prototype's loss-free burst result applies to the extension.

Next integration work must implement a private authenticated local endpoint, bounded request admission/backpressure, Go acknowledgment and same-ID spool fallback, lease-aware shutdown, publisher-config versioning, and T23 generation/reset cleanup. Exercise collector absence, full queues, invalid tokens, privacy changes, stale generations and kill points before repeating installed resource qualification. Near-cap memory and final idle CPU remain independent open findings.

Current core validation: strict contracts/types/build, 172 unit tests with no skips outside the shell sandbox, 23 actual process tests, and Go tests. The new process case kills the collector after batch sync/before acknowledgment and verifies replay plus spool retries without a second durable effect. The final [40-check installed Cursor regression](t22-final-extension-host-verification.json) passed after the batch/polling edits. Publisher is disabled, hooks/lease absent and inbox empty. Cursor 3.26.16 and Go 1.27.3 were read from the actual installed build/toolchain.

The follow-up [real-journal API prototype](t22-batch-journal-api-prototype.json) also passed all 2,000 distinct records with zero client errors and 28.18 ms helper-close p95, using 747 durable groups (maximum queue 13). It exercises the actual batch writer, source/scope validation, lease checks and a static valid privacy admission policy. Synthetic source construction and missing production endpoint/auth/fallback/reset integration remain explicit; this does not close T22.


## Production broker transport measurement — 26 October 2026 (Pacific)

[Production broker burst](t22-production-broker-burst.json) used the compiled Go helper and production authenticated broker/journal: 2,000 attempts, 2,000 accepted, zero duplicate/rejected/failure counters, no pending inbox files, and helper-close p95 26.46 ms. The separate producer sustained the ten-second schedule. Collector incremental RSS for this small-history burst was 29,523,968 bytes; this is not the near-cap replay measurement or shared installed-host memory. Synthetic helper input does not establish ordinary native Agent delivery or provider visibility. T22/G3/T24 remain open. Reproduce sequentially with `node scripts/measure-generation-burst.mjs --broker --output=t22-independent-broker.json`.

[Installed broker measurement](t22-production-broker-editor-performance.json) observed 2,041/2,041 expected events, including the 2,000-event burst. Normal compiled-helper close p95 was 27.79 ms and matching provider-row p95 was 218.77 ms. Burst helper-close p95 was 55.00 ms, exceeding the 50 ms target if that target applies throughout burst load. First helper close was 243.47 ms. Loaded shared-host idle CPU was 2.63% of one core, versus 1.00% disabled and 3.35% empty-enabled; the loaded-minus-disabled estimate was 1.63 percentage points. These raw controls must remain visible. Shared-host incremental peak RSS was 376,717,312 bytes (about 359 MiB), exceeding 75 MiB even for this small-history burst. This is a different scope from standalone near-cap replay. The host run passed its delivery assertion, not the CPU/memory budgets. No budgets were changed.

## Cold replay lifetime improvement — 26 October 2026 (Pacific)

The [current broker-era near-cap baseline](t22-broker-history-window.json) validated 97,280 records and projected the latest 5,000, peaking at 225,951,744 incremental RSS bytes. A local heap snapshot did not support the proposed sliced-UUID-string retention hypothesis. The snapshot operation occurs after the memory samples; that baseline report's completion duration includes profiling overhead and must not be compared as replay timing. The reader harness now freezes completion duration before optional snapshot work.

[Index-first cold replay](t22-history-index-first.json) validates all retained bytes into the compact identity index, applies retention, then hydrates only the last 5,000 payloads via validated bounded history reads. It no longer cycles every older payload through the recent window. This adds a read of the recent segments. In the measured run, incremental peak RSS was 128,090,112 bytes (about 122 MiB), first projection began at 2,448.69 ms, and the full recent projection completed at 7,305.11 ms with explicit staged-loading status. The 75 MiB target remains unmet. No GC was forced during either measured interval; fixture size/record counts are unchanged. The prior installed broker performance report predates this cold-load change and remains historical evidence for that implementation.

The settled-idle V8 profile of the broker/index-first implementation is retained locally at `.local/t08-extension-tests-t22-broker-idle-profile/idle.cpuprofile`. Approximately 22 ms of leaf samples landed in Overwatch JavaScript during a 15.2-second profile; approximately 212 ms landed in inspector `post`, with additional GC, runtime and editor work. Profiled process idle CPU was 4.13%, versus its 1.01% disabled control. Sampling does not attribute all native, filesystem, worker or IPC cost, and profiler overhead makes this unsuitable as a replacement for the unprofiled 2.63% loaded sample. It does not establish a CPU-budget pass or justify speculative polling/render changes.
